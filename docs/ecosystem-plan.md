# Мастер-план: канбан → единая экосистема (подробная редакция)

_Ветка: `feature/ecosystem` · дата: 2026-06-14_

Документ детализирует каждый пункт с учётом реальных нюансов кодовой базы.
Сопутствующее: краткий чат-план — `docs/chat-plan.md`; конвенции — память `kanban-ecosystem-service-pattern`.

---

## 0. Исходная задача и принцип

Канбан перестаёт быть корнем и становится **одним из сервисов** под единым интерфейсом и общей
ролевой моделью. Сервисы: **Wiki** (Confluence-аналог, WYSIWYG + роли), **Чат**, **Календарь**,
**Почта** (свой почтовый сервер + веб-клиент). Качество — как у канбана, не «для галочки».

**Цикл каждого сервиса:** backend (store + handler) → тесты → frontend (`<name>.js`) →
интеграция в общий UI/realtime → e2e-проверка. Каждый рабочий инкремент = отдельный коммит.

## 1. Сквозные нюансы (касаются ВСЕХ фаз)

Эти механизмы общие; каждый новый сервис обязан их соблюдать.

1. **Реестр сервисов** (`internal/handler/services.go`): добавить имя в `serviceOrder`,
   `serviceAvailable[name]=true` (иначе сервис невидим в UI и API), `serviceDefaultOn`.
   Состояние вкл/выкл — в `app_settings` ключом `svc_<name>_enabled`, читается `serviceEnabled()`.
   Каждый хендлер сервиса в начале проверяет `serviceEnabled` (для чата — через `chatUser()` → 404).

2. **Центральный middleware `Handler.ServeHTTP`** (handler.go:146): задаёт CSP/security-заголовки,
   гейтит публичные пути, проверяет setup/сессию, кладёт юзера в контекст (`currentUser(r)`).
   **Read-only гейт** (строка 208): роль `readonly` не может делать не-GET, КРОМЕ явного списка
   исключений. Любой «безопасный» POST нового сервиса (как `/api/chat/.../read`) нужно добавить
   в этот список, иначе 403.

3. **Слой БД — SQLite, `SetMaxOpenConns(1)`** (store.go:74, WAL + busy_timeout + foreign_keys=on).
   Одно соединение: открытый курсор держит его целиком → в store СНАЧАЛА полностью прочитать
   `rows`, и ТОЛЬКО ПОТОМ делать follow-up запросы (паттерн `ListChatChannels`). Иначе дедлок.
   Миграции — добавлять `CREATE TABLE IF NOT EXISTS` в `store.migrate()` + индексы под FK-выборки.

4. **Ролевая модель:** глобально `admin`/`regular`/`readonly` (`model.User.Role`). Для совместного
   доступа внутри сервиса — паттерн per-resource ACL как в wiki (`effectiveWikiRole`:
   admin/editor/viewer + visibility open/restricted). Брать его за образец для календаря/почты.

5. **Frontend — единый SPA в одном `web/templates/index.html` (~245KB)** + отдельный
   `web/static/js/<name>.js`, подключаемый `<script>` (рядом с `wiki.js`, строка ~12):
   - функция `render<Name>View()` переопределяет заглушку (`renderServiceStub`), её вызывает
     `renderCurrentView()` (switch по `currentView`, строка ~1026) и app rail;
   - навигация — `navigateTo('/<name>')`; rail рисует `renderAppRail()`, бейдж — `setRailBadge(name,n)`;
   - **i18n обязателен**: ключ `svc_<name>` уже есть во всех ~10 языках; все строки UI — через `t()`,
     добавлять во ВСЕ языки; учитывать тему и RTL (арабский);
   - **XSS**: пользовательский текст экранировать `esc()`; HTML-контент — санитайзить (`sanitize.go`).

6. **Уведомления — двойной канал:** `store.CreateNotification(userID, type, text, taskID)` (in-app) +
   `h.sendTelegramNotification(userID, text)` (Telegram). Тип — строка (`model.Notification.Type`,
   напр. `chat_mention`). Новые типы добавлять консистентно; учитывать в центре уведомлений (Фаза D).

7. **Вложения и сборка мусора — ВАЖНЫЙ НЮАНС/БАГ.** Загрузка файлов/картинок переиспользуема:
   backend `handleFileUpload`/`handleImageUpload` + таблицы `files`/`images`; frontend
   `triggerFileAttach` + `compressImage` + `MAX_UPLOAD_SIZE`. НО `CleanupOrphanFiles` (store.go:1170)
   сканирует ссылки `/api/(images|files)/N` **только в `comments` и `tasks.description`**.
   Вызывается при удалении задачи/комментария, перед каждым бэкапом и в дневном шедулере.
   ⚠️ Значит файлы, на которые ссылаются **wiki-страницы и чат-сообщения, будут удалены как сироты**
   (для wiki это уже латентный баг). **Любой сервис с вложениями обязан** расширить
   `CleanupOrphanFiles`, чтобы она сканировала и его текстовые таблицы (`wiki_pages.content`,
   `wiki_revisions.content`, `chat_messages.text`, будущие тела писем).

8. **Экспорт/импорт и бэкапы — НЮАНС.** `ExportAll`/`ImportAll` (JSON, store.go:1349/2123) покрывают
   только ядро канбана (users, settings, tasks, deps, subs, files, images). **Wiki и chat НЕ
   экспортируются** → при JSON-восстановлении теряются. Полный бэкап `.db`-файла их сохраняет, но
   JSON-экспорт нужно расширять под каждый сервис (модель `ExportData`, `exportXxx`/импорт-ветки).

9. **SSE-реалтайм:** хаб `sseHub`/`sseEvent` сейчас живёт в `chat.go`, подписка per-userID, адресная
   рассылка/broadcast, heartbeat. Для realtime в календаре/почте — либо обобщить хаб (вынести из
   chat.go в общий модуль и расширить типы событий), либо переиспользовать как есть. Решить в Фазе B.

10. **Таймзоны:** `getTimezone()` (frontend) + `/api/settings/timezone`. Календарь обязан быть
    timezone-aware (хранить UTC, отображать в TZ пользователя).

11. **HTML-санитайзер** (`sanitize.go`, 335 строк) — единая точка очистки HTML (используется wiki).
    Тела писем в формате HTML (Фаза C) обязаны проходить через него перед рендером.

12. **WAP** (`wap.go`) — отдельная WML-версия для кнопочных телефонов, только для канбана.
    Новым сервисам WAP не требуется (не усложнять).

### A2. Frontend `web/static/js/chat.js` (по образцу `wiki.js`)

- **Лента**: `GET /api/chat/channels/{id}/messages` (limit/ before для подгрузки вверх),

- **Отправка/редактирование/удаление**: `POST /messages`, `PUT/DELETE /api/chat/messages/{id}`;

- **Прочитано**: `POST /api/chat/channels/{id}/read` с максимальным виденным `id` при открытии/скролле.
- **Управление**: создание канала/группы (`POST /channels`), участники (`/members`),
  старт DM (`POST /api/chat/dm`); права рисовать по `chatCanManage` (admin/создатель).
- **Поиск**: `GET /api/chat/search?q=` (debounce, как в wiki — 300мс).
- **@-упоминания**: автодополнение из списка пользователей (`/api/users`); подсветка в ленте.
- **i18n**: добавить все строки чата в `t()` во все языки.

## 4. ФАЗА B — Календарь

- Миграции: `calendars` (id, name, owner_id, type личный/командный/проектный, color),

## 5. ФАЗА C — Почта: свой почтовый сервер (MTA)

Самая тяжёлая и инфраструктурно-зависимая фаза. Делается ПОСЛЕДНЕЙ, мелкими под-фазами; каждый
протокол — отдельный модуль. ⚠️ В песочнице нет внешней сети/DNS и запрещён podman — реальную
доставку наружу полноценно не проверить; тестируем локально (приём, перехват очереди, юнит-тесты).

### C1. Хранилище и модель (без сети, тестируется первым)
- Миграции: ящики (привязка к `users`), `mail_folders` (Inbox/Sent/Drafts/Trash/кастом),
  `mail_messages` (RFC 5322: from/to/cc/subject, тело text + html, raw, флаги Seen/Flagged/
  Answered/Deleted, размер, timestamps), `mail_attachments` (или переиспользовать `files`),
  треды (`thread_id`/`in_reply_to`/`references`). Индексы по folder/thread/date.
- Store + тесты (модель, флаги, треды) — первым и без сети.

### C2. SMTP-приём входящих
- SMTP-сервер на отдельном порту (Go: `emersion/go-smtp`), парсинг MIME (`emersion/go-message`),
  раскладка по ящикам/папкам, лимиты размера, hook под антиспам.
- ⚠️ Это добавит **первую внешнюю зависимость сверх `go-sqlite3`** — отступление от принципа
  «zero deps» из README. Зафиксировать решение явно (альтернатива — свой парсер, дороже/рискованнее).

### C3. SMTP-отправка исходящих
- Очередь, доставка на внешние MX, ретраи, генерация bounce. Локально — sink/перехват для тестов.

### C4. IMAP-доступ (опционально)
- Для внешних почтовых клиентов — `emersion/go-imap`; либо доступ только через веб-API.
  Решить в начале под-фазы.

### C5. Безопасность доставки
- TLS (STARTTLS/implicit), проверка SPF входящих, DKIM-подпись исходящих, DKIM/DMARC-проверка
  входящих. Требует DNS-записей (MX/SPF/DKIM/DMARC) — настраивается ВНЕ кода при развёртывании.

### C6. Web-API + frontend `mail.js`
- API роуты `/api/mail/*` (папки, письма, отправка, поиск); read-only исключения при необходимости (§1.2).
- `mail.js`: список папок, тред-вид, композер (вложения через `triggerFileAttach`), поиск, бейдж
  непрочитанных; **HTML-тела писем — через `sanitize.go`** (§1.11); i18n; `esc()`.
- ⚠️ Вложения писем — учесть в `CleanupOrphanFiles` (§1.7) либо своя модель владения.

### C7. e2e
- Юнит-тесты MIME/DKIM/очереди; локальная петля приём→ящик→веб-клиент; build/vet/test; коммиты.

## 7. Ограничения процесса
- **Без `git push` и `podman`** (в `deny`). Локальный запуск — только `go run` (kanban.sh = podman).
- **Только ветка `feature/ecosystem`**, не main. Коммит после каждого рабочего инкремента.
- Файлы — Read/Edit/Write; нестандартное — через `python3`. Без `$(...)`/бэктиков/env-префиксов в Bash.
- БД: `SetMaxOpenConns(1)` → read-all-then-followup.

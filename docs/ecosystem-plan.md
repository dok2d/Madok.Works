# Мастер-план: канбан → единая экосистема

_Ветка: `feature/ecosystem` · дата: 2026-06-14_

## 0. Исходная задача

Сделать канбан **не основным приложением, а частью экосистемы** под единым интерфейсом и
ролевой моделью (роли уже есть). Сервисы экосистемы:

1. **Wiki** — аналог Confluence: структурированная документация, WYSIWYG-редактор, ролевые модели.
2. **Чат** — каналы/группы/личные сообщения.
3. **Календарь**.
4. **Почта** — почтовый сервер + веб-клиент в интерфейсе пользователя.

Требование: сервисы должны быть **в едином гармоничном интерфейсе** и сделаны так же
**скрупулёзно, как канбан** (не «для галочки», как в прошлой кривой попытке —
ветка `claude/kanban-ecosystem-integration-bnjJA`).

---

## 1. Архитектурный подход (что делает интерфейс единым)

Уже заложен каркас, на котором держится «единство»:

- **App rail** (левая/нижняя панель) — переключение между канбаном и сервисами,
  бейджи непрочитанного. Канбан стал одним из элементов rail, а не корнем.
- **Реестр сервисов** (`services.go`): `serviceOrder`, `serviceAvailable`, `serviceDefaultOn`,
  тогглы в админке, состояние в `app_settings` (`svc_<name>_enabled`). Сервис включается
  фазами — пока код не готов, он невидим.
- **Единый роутинг вьюх** (`renderCurrentView` в index.html) уже знает про `wiki/chat/calendar/mail`.
- **Сквозные системы**, переиспользуемые всеми сервисами: аутентификация (вкл. LDAP/OIDC),
  ролевая модель, уведомления (in-app + Telegram), поиск, i18n (~10 языков), тема/RTL,
  единый слой БД (SQLite, WAL, `SetMaxOpenConns(1)`).

**Принцип качества:** каждый сервис = backend (store + handler) → тесты → frontend (`<name>.js`)
→ realtime/интеграция в общий интерфейс → e2e-проверка. Каждый рабочий инкремент — отдельный коммит.

Детали конвенций — в памяти `kanban-ecosystem-service-pattern`.

## 3. Этапы (роадмап)

### Фаза A — Чат (в работе)
Подробный план — `docs/chat-plan.md`. Кратко:
- **A0** закоммитить готовый backend ← немедленный шаг.
- **A1** тесты backend.
- **A2** frontend `chat.js` (по образцу `wiki.js`).
- **A3** realtime (SSE) + бейджи непрочитанного в rail.
- **A4** e2e-проверка (`go run`, не podman) → коммит.

### Фаза B — Календарь
- **B1 backend**: модель событий (заголовок, время начала/конца, all-day, повтор/RRULE,
  место, описание, участники), календари (личный/командный/по проектам), права через
  существующую ролевую модель. Store + хендлеры CRUD, выборка по диапазону дат.
- **B2** интеграции: события из задач канбана (дедлайны/спринты) на календаре; напоминания
  через систему уведомлений (in-app + Telegram).
- **B3 тесты** backend (диапазоны, повторы, права).
- **B4 frontend** `calendar.js`: виды месяц/неделя/день/повестка, создание/перетаскивание
  событий, переключение календарей. Бейдж ближайших напоминаний.
- **B5** e2e-проверка → коммиты по инкрементам.

### Фаза C — Почта: свой почтовый сервер (MTA) ⬅ выбран scope
Самая тяжёлая фаза. Полноценный self-hosted почтовый сервер + веб-клиент. Разбить на под-фазы,
коммитить мелкими инкрементами; каждый протокол — отдельный модуль.

- **C1 Хранилище и модель** (без сети, тестируется первым): пользователи-ящики,
  папки (Inbox/Sent/Drafts/Trash/кастом), письма (RFC 5322: заголовки, тело text/html,
  вложения как MIME), треды, флаги (Seen/Flagged/Answered/Deleted). Store + миграции + тесты.
- **C2 SMTP-приём (входящие)**: SMTP-сервер на отдельном порту (Go, напр. `emersion/go-smtp`),
  парсинг MIME (`go-message`), раскладка по ящикам, лимиты размера, базовый антиспам-хук.
- **C3 SMTP-отправка (исходящие)**: постановка в очередь, доставка на внешние MX, ретраи,
  bounce-сообщения. Локально — sink/перехват для тестов (без реальной сети).
- **C4 Доступ по IMAP** (для внешних клиентов) — опционально, через `go-imap`; либо
  внутренний доступ только через веб-API. Решить в начале C4.
- **C5 Безопасность доставки**: TLS (STARTTLS/implicit), SPF-проверка входящих,
  DKIM-подпись исходящих + DKIM/DMARC-проверка входящих. Требует DNS-записей (MX/SPF/DKIM/DMARC)
  на стороне инфраструктуры — вне кода.
- **C6 Web-API + frontend** `mail.js`: список папок, тред-вид, композер (вложения через готовый
  `triggerFileAttach`), поиск, бейдж непрочитанных, привязка к ролям/пользователям.
- **C7 e2e-проверка** → коммиты.

> ⚠️ **Ограничения окружения:** podman запрещён, а в песочнице нет внешней сети/DNS, поэтому
> реальную доставку наружу (C3/C5) полноценно проверить нельзя — тестировать через локальный
> SMTP-приём, перехват очереди и юнит-тесты MIME/DKIM. Боевая часть (MX/SPF/DKIM/DMARC, публичный
> IP, обратный DNS, TLS-сертификаты) настраивается при реальном развёртывании.

### Фаза D — Полировка экосистемы (сквозная)
- **Глобальный поиск** по всем сервисам (канбан/wiki/чат/календарь/почта) в едином окне.
- **Единый центр уведомлений** (упоминания в чате, события календаря, новые письма, задачи).
- Сверка единообразия UI/UX, темы, RTL, i18n во всех сервисах.
- Документация (README/en-docs) по экосистеме.

## 4. Решение по scope почты ✅

**Выбрано: свой почтовый сервер (MTA)** — полноценный self-hosted (приём по SMTP, хранение,
отправка наружу, DKIM/SPF/DMARC, TLS) + веб-клиент. Детализация — в Фазе C (§3).

Это самый объёмный и инфраструктурно-зависимый сервис, поэтому: делается **последним** (после
чата и календаря), дробится на под-фазы C1–C7, а боевая доставка наружу настраивается уже при
реальном развёртывании (в песочнице без сети/DNS проверяется только локально).

---

## 5. Ограничения процесса
- **Без `git push` и `podman`** (в `deny`). Локальный запуск — только `go run` (kanban.sh = podman).
- **Только ветка `feature/ecosystem`**, не main. Коммит после каждого рабочего инкремента.
- Файлы — Read/Edit/Write; нестандартное — через `python3`.
- БД: `SetMaxOpenConns(1)` → в store сначала прочитать все строки, потом follow-up запросы.
